## 一、背景

几个人一起吃饭、出去玩、合租，经常会出现一个人先垫钱、之后再互相还的情况。现在大家处理这件事的方式主要有三种：

1. 微信群里口头说一句"我先付，回头找你要"，然后忘掉
2. 用记事本或者 Excel 记，但每次都要手动算
3. 用 Splitwise、Tricount 这类工具

第三种是目前最好的方案，但它有一个共同问题：**录入太麻烦**。用户要打开 App、新建一笔账单、填金额、选参与人、选分摊方式，一顿饭要点七八下。结果就是很多人下载了但没用几次，最后还是回到"算了不算了"。

我们认为这里有机会：录入环节可以做得比现有产品轻很多。用户拍一张小票，或者用一句话描述，剩下的交给系统。

## 二、目标

### 2.1 本期要解决的问题

让用户记一笔账的操作成本从"填一张表"降到"拍一张照"或"说一句话"。

### 2.2 成功指标

MVP 上线后一个月内观察：

- 单笔账单平均录入耗时低于 15 秒
- 通过拍照或自然语言录入的账单占比达到 40% 以上
- 收据识别的金额准确率达到 90% 以上（以用户是否修改金额为准）
- 新建群组后 7 天内仍有记账行为的群组占比达到 30%

### 2.3 本期不追求的

- 不追求用户量
- 不追求商业化
- 不做社交、内容、分享相关的功能

## 三、目标用户

**主要用户**：20 到 35 岁，有固定的小圈子会经常一起花钱的人。具体包括：

- 合租室友（水电燃气网费、日用品）
- 经常一起出去玩的朋友（吃饭、打车、门票）
- 情侣（日常开销）

**关键特征**：这些人对钱的绝对数额不敏感（一顿饭一两百），但对"算不清楚"这件事本身敏感。他们需要的不是省钱，是省掉尴尬。

**典型场景**：

> 五个人在外面吃饭，小李用自己的卡结了 238。其中小王没喝酒，Lucy 点了一份龙虾，Tom 只喝了杯咖啡。小李想把这笔账记下来，但不想在饭桌上掏出手机点十几下。

## 四、名词说明

| 名词 | 含义 |
|---|---|
| 群组 (Group) | 一组会重复一起花钱的人，比如"深圳租房"、"夏威夷旅行" |
| 账单 (Expense) | 一笔具体的支出，包含金额、付款人、参与人和分摊方式 |
| 分摊 (Share) | 某个参与人在这笔账单中应承担的金额 |
| 净额 (Net Balance) | 一个人在群组中的总垫付减去总应付，正数代表别人欠他 |
| 结算方案 (Settlement) | 系统计算出的一组转账建议，执行完之后所有人净额归零 |
| 结清 (Settle Up) | 用户手工确认某笔转账已经完成 |

## 五、功能需求

优先级说明：P0 表示不做就无法上线，P1 表示尽量在 MVP 内完成，P2 表示可以砍。

### 5.1 账号与群组

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-101 | 用户可以用手机号或邮箱注册登录 | P0 |
| FR-102 | 用户可以创建群组，填写群组名称 | P0 |
| FR-103 | 用户可以通过分享链接邀请他人加入群组 | P0 |
| FR-104 | 被邀请人点击链接后，未注册的先注册再自动入群 | P0 |
| FR-105 | 群组内可以添加"虚拟成员"（只有名字、没有账号的人） | P1 |
| FR-106 | 群组创建者可以移除成员，但净额不为零的成员不能被移除 | P1 |
| FR-107 | 用户可以退出群组，净额不为零时需要先结清 | P1 |

**说明**：FR-105 很重要。实际场景里总有一两个人不愿意下载 App，如果强制所有人注册，整个群组就用不起来了。虚拟成员由创建者代为记账，后续可以关联到真实账号。

### 5.2 手动记账

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-201 | 用户可以在群组内新建账单，填写金额、说明、日期 | P0 |
| FR-202 | 用户可以指定付款人，默认是自己 | P0 |
| FR-203 | 用户可以选择参与人，默认全选群组成员 | P0 |
| FR-204 | 支持三种分摊方式：均分、按比例、按金额 | P0 |
| FR-205 | 分摊金额之和必须等于账单总额，不等时不允许提交并提示差额 | P0 |
| FR-206 | 均分产生的余数（如 100 除以 3）自动分配，不允许出现小数分 | P0 |
| FR-207 | 用户可以编辑和删除自己创建的账单 | P0 |
| FR-208 | 账单支持添加分类标签（餐饮、交通、住宿、日用、其他） | P2 |

**关于 FR-206**：100 元三个人均分，结果应该是 33.34 / 33.33 / 33.33，不能是三个 33.33。余数给谁需要有固定规则（建议给付款人，或者按成员顺序轮流），不能每次刷新结果不一样。

### 5.3 收据识别

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-301 | 用户可以拍照或从相册选择收据图片 | P0 |
| FR-302 | 系统识别出商家名称、总金额、税费、小费 | P0 |
| FR-303 | 系统识别出逐项商品名称和单价 | P0 |
| FR-304 | 识别结果以可编辑的列表展示，用户可以修改任意字段 | P0 |
| FR-305 | 用户可以为每一项商品单独勾选参与人 | P0 |
| FR-306 | 税费和小费按各人商品小计的比例自动分摊 | P0 |
| FR-307 | 识别失败或超时（10 秒）时，降级到手动录入并保留图片 | P0 |
| FR-308 | 商品项之和与识别出的总金额不一致时，给出提示但不阻断 | P1 |
| FR-309 | 收据原图保存并可在账单详情中查看 | P1 |

**说明**：FR-304 和 FR-307 是这个功能能不能用的关键。识别一定会出错，产品设计上必须假设"每次都可能错"，而不是"偶尔会错"。用户改一个数字的成本，要远低于重新录入一遍。

### 5.4 自然语言记账

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-401 | 用户可以在输入框里用一句话描述一笔支出 | P0 |
| FR-402 | 系统解析出金额、付款人、参与人、分摊方式 | P0 |
| FR-403 | 解析结果以结构化表单展示，提交前用户可以修改 | P0 |
| FR-404 | 解析出的人名需要匹配到群组内的真实成员，匹配不上时提示用户手动指定 | P0 |
| FR-405 | 无法解析时，把原文填到账单说明里，让用户手动补齐金额和分摊 | P0 |
| FR-406 | 支持语音输入转文字 | P2 |

**输入示例**：

```
今晚聚餐我付了 238，小王没喝酒，Lucy 吃了龙虾，Tom 只喝咖啡
```

**期望解析结果**：

```
金额：238
付款人：当前用户
参与人：当前用户、小王、Lucy、Tom
分摊方式：需要用户确认（因为消费不均等）
备注：今晚聚餐
```

**说明**：这个例子里系统其实无法准确判断每个人该出多少，因为没有单价信息。此时不要瞎猜，应该把识别到的信息填好，把分摊比例留给用户调整。**宁可少做一步，不要做错一步**。

### 5.5 余额与结算

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-501 | 群组首页展示每个成员当前的净额 | P0 |
| FR-502 | 用户可以查看自己与某个成员之间的明细往来 | P0 |
| FR-503 | 系统计算最少转账笔数的结算方案 | P0 |
| FR-504 | 结算方案中每一笔转账都要能追溯到来源，说明为什么是这两个人之间转账 | P0 |
| FR-505 | 用户可以关闭"简化债务"，改为按原始欠款关系逐笔结算 | P1 |
| FR-506 | 用户可以标记某笔转账为已完成，标记后净额相应更新 | P0 |
| FR-507 | 被标记的一方收到通知，可以确认或申诉 | P1 |
| FR-508 | 群组内所有人净额归零时，展示一个结清提示 | P1 |

**关于 FR-504 和 FR-505**：简化债务会让 A 突然需要转账给一个不太熟的 C。金额是对的，但用户会困惑。所以要么提供解释链（"你欠 B 50，B 欠 C 50，所以直接付给 C"），要么允许用户关掉这个功能。Splitwise 在这一点上收到过很多负面反馈。

### 5.6 通知

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-601 | 有新账单涉及自己时，推送通知 | P1 |
| FR-602 | 有人标记向自己转账时，推送通知 | P1 |
| FR-603 | 用户可以关闭群组维度的通知 | P2 |

## 六、主要流程

### 6.1 拍照记账流程

```
进入群组
  → 点击拍照按钮
  → 拍摄或选择收据
  → 等待识别（页面展示进度，超过 10 秒降级）
  → 展示识别结果列表
  → 逐项勾选参与人（默认全员）
  → 确认提交
  → 返回群组，余额更新
```

### 6.2 结算流程

```
进入群组
  → 点击"结算"
  → 展示结算方案（谁付给谁、多少钱）
  → 用户点击某一笔转账
  → 展示这笔转账的构成来源
  → 用户线下完成转账后，点击"已支付"
  → 净额更新，对方收到确认通知
```

## 七、非功能需求

| 编号 | 需求 |
|---|---|
| NFR-01 | 所有金额在数据库中以"分"为单位的整数存储，不使用浮点数 |
| NFR-02 | 收据识别响应时间 P90 低于 5 秒，超过 10 秒降级 |
| NFR-03 | 群组内成员的余额数据需要保持最终一致，多人同时记账不能出现金额丢失 |
| NFR-04 | 账单的所有修改和删除操作需要留存操作记录，可追溯 |
| NFR-05 | 支持中文和英文界面 |
| NFR-06 | 首期只做 Web 端（移动端浏览器适配），不做原生 App |

**关于 NFR-01**：这个必须在第一天就定下来。用浮点数存钱会在分摊余数上产生累积误差，几个月后余额永远清不了零，而且这类问题极难排查、极难修复历史数据。

## 八、数据埋点

需要记录的关键事件：

| 事件 | 参数 |
|---|---|
| 群组创建 | 群组 ID、创建人 |
| 账单创建 | 账单 ID、录入方式（手动 / 拍照 / 自然语言）、耗时 |
| 收据识别完成 | 是否成功、耗时、识别项数 |
| 收据识别结果被修改 | 修改了哪些字段、修改次数 |
| 自然语言解析完成 | 是否成功、解析出的字段数 |
| 结算方案生成 | 原始笔数、简化后笔数 |
| 转账标记完成 | 金额、距离账单创建的天数 |

其中"识别结果被修改"这个事件最重要，它直接反映识别质量。如果用户每次都要改金额，说明这个功能没有价值。

## 九、本期不做

以下功能在需求讨论中提到过，明确不在 MVP 范围内：

| 功能 | 原因 |
|---|---|
| 旅行时间轴（照片、地图、收据聚合） | 依赖足够多的历史数据才有展示效果，新用户账本是空的 |
| 关系画像（消费统计、请客次数、结算习惯） | 同上 |
| 旅行消费总结与分享 | 同上 |
| 多币种 | 增加汇率、汇率时点、结算币种等一系列问题，MVP 用户以本地消费为主 |
| 周期性账单（房租、水电） | 需要额外的调度和提醒机制，可以先用手动记账替代 |
| 对接支付平台一键转账 | 涉及资质和合规，周期不可控 |
| 支付方式约束（只能用 Venmo / 支付宝） | 会把结算算法从"最少笔数"变成带约束的图匹配，复杂度上升明显 |
| 原生 App | 先用 Web 验证核心流程 |

虽然本期不做，但**数据模型需要提前预留字段**：账单表要留 `trip_id`、`location`、`photo_urls`，否则后续做旅行时间轴时无法补齐历史数据。
