# Quits

Split bills. Settle clean.

多人共享记账工具。拍一张小票或者说一句话，系统算出谁欠谁多少钱，给出转账笔数最少的方案，并解释每一笔为什么是这两个人之间转账。

这是一个从需求文档到实现的完整练习项目，只在本地运行，不部署。中英双语。

---

## 为什么做这个

几个人一起吃饭、出去玩、合租，经常有人先垫钱、之后再互相还。现在的处理方式无非三种：在群里口头说一句然后忘掉、用 Excel 手动算、或者用 Splitwise 这类工具。

第三种是目前最好的，但它有个共同问题：**录入太麻烦**。用户要新建账单、填金额、选参与人、选分摊方式，一顿饭点七八下。结果就是很多人下载了没用几次，最后还是回到"算了不算了"。

所以这个项目没有做成"更好看的 Splitwise"，而是集中解决两件事：

1. 把记一笔账的成本从"填一张表"降到"拍一张照"
2. 让简化后的结算方案能被解释清楚，而不只是给出一个正确但让人困惑的结果

---

## 主要功能

**记账**
- 拍收据自动识别商品项和金额，逐项勾选谁吃了什么，税费小费按比例分摊
- 一句话记账（"昨天打车 45，我和 Lucy 平摊"），信息不全时最多追问 3 轮
- 手动录入，支持均分、按比例、按金额三种分摊
- 付款人不必参与分摊（帮别人垫钱的场景）

**结算**
- 计算转账笔数最少的方案，并展示"直接结算 4 笔 → 简化后 3 笔"的对比
- 每一笔转账可展开，说明双方的欠款分别来自哪几笔账单
- 可关闭简化，退回逐对结算
- 支持部分还款

**数据**
- 关系画像：两个人之间的共同消费、请客次数、承担比例、结算习惯
- AI 消费总结：把统计结果翻译成自然语言，只陈述事实不给建议
- 账单搜索、多选分类筛选，筛选结果实时显示笔数与合计

**其他**
- 中英双语，界面语言、AI 输出、日期与货币格式统一切换
- 注册可选，也可以不建账号直接开始记账
- 软删除与回收站，保留 30 天，支持多选批量操作
- 导出摘要图片，可直接发到群里
- 每个群组一种货币，支持常见币种

## 几个做过取舍的决定

这部分是这个项目里我认为比功能本身更值得说的内容。

### 1. 金额全部用整数「分」存储

数据库里没有任何 Float 或 Decimal 字段，所有金额字段以 `Cents` 结尾，只在渲染的那一刻才除以 100。

分摊必然产生除不尽的情况（100 元三个人）。如果用浮点数，每笔账单漏掉的零点几分会不断累积，几个月后余额永远清不了零，而且这类问题极难定位、历史数据无法修复。

余数用最大余数法分配，有测试保证 `sum(shares) === total` 恒成立，包括 1 分钱分给 3 个人这种边界。

**代价**：所有涉及金额的代码都要处理单位转换，比直接用小数啰嗦。

### 2. 结算算法用精确解，但承认贪心已经够用

最少转账笔数是 NP-hard 的（等价于把一组和为零的数字最多划分成几个和为零的子集）。实现上先做净额化消掉环形债务，再用位掩码 DP 找出最多的零和子集，子集内部贪心配对。人数超过 15 时退回纯贪心。

实测下来贪心在大部分情况已经是最优的，精确解只在"人群天然分成几个独立小圈子"时更好。比如净额是 `{A:+10, B:-6, C:-4, D:+6, E:-6}` 时，贪心要 4 笔，精确解 3 笔。

**代价**：多写了几十行 DP，收益场景其实不多。留下它是因为实现成本低，而且这个差异正好能演示出来。

### 3. 简化债务必须给出解释

简化后 A 可能需要转钱给一个不太熟的 C。金额是对的，但用户会困惑——Splitwise 因为这个被吐槽了很多年。

所以每一笔转账都可以展开，说明付款人的欠款来自哪几笔账单、收款人垫付了哪几笔，以及当两人之间没有直接欠款时，明确写一句"这是系统合并多笔债务后的结果"。同时保留关闭简化的开关。

这条是整个项目里最坚持的一个设计。算得对不等于用得对。

### 4. 收据识别和自然语言记账是同一个模块

两者输入类型不同（图片 / 文字），但走同一个模型调用、返回同一个 JSON schema、接同一个可编辑的确认表单。写成两套是纯粹的浪费。

识别结果一律进可编辑表单而不是只读预览，因为识别一定会出错。产品设计上假设的是"每次都可能错"，而不是"偶尔会错"——用户改一个字段的成本，必须远低于重新录入一遍。

### 5. 模型只做翻译，不做计算

AI 消费总结不接收任何原始账单数据，只接收已经算好的聚合统计（分类金额、月度趋势、承担比例、结算习惯）。

两个原因：账单明细是隐私数据；更实际的是，模型拿到一百多条记录会自己去算总和，然后算错。

同理，模型返回的句子里不写死金额，而是用 `{amount}` 占位符，数值单独放在字段里，由前端统一格式化。这样千分位、小数位、货币符号永远一致，不会出现文案写 `¥2760.00` 而徽章写 `$2,760.00` 的情况。

### 6. AI 总结只陈述事实，不给建议

早期版本会输出"你们在咖啡上花得较多，可以考虑控制"这类内容。后来全部去掉了。

分账工具介入两个人之间的钱，本身就是敏感的事。系统说"你承担的比例偏高"，可能让本来不计较的人开始计较——这恰好是这个产品想解决的问题的反面。

所以只保留客观陈述：「最近三个月共 42 笔支出，合计 ¥3,820，餐饮占 46%」。判断留给用户。

### 7. Mock 模式是有意保留的，不是没做完

`MOCK_AI=true` 时解析模块不发任何网络请求，直接返回预置结果。

没有 API key 的人也能完整跑起来；演示时不会因为网络、超时或模型抽风而中断；测试可以断言确定性的结果。Mock 和真实调用共用同一个函数签名和返回结构，切换只改一个环境变量。

另外，输入少于 5 个字符或不含任何数字时，直接本地拦截不发请求。什么该交给模型、什么不该，是这个项目里反复出现的判断。

### 8. 注册是可选的，不是入口门槛

首屏有完整的注册和登录，但下面并排放着一个同样大小的「直接开始记账」，只填一个名字就能用。

记账场景里强制注册是最大的流失点——总有一两个人不愿意为了一顿饭注册账号，一旦强制，整个群组就用不起来了。项目里的「虚拟成员」设计（有名字、没有账号，由他人代记账）就是在解这个问题。

所以注册不锁任何功能。AI 解析、关系画像、导出，不注册全都能用。注册的唯一价值是跨设备同步，这个价值在用户已经记了十几笔账之后才成立，那时候再提示比在门口拦住人更有效。

「直接开始」按钮下面写了两行字：一行讲代价（数据只在这台设备上），一行讲退路（之后可以在设置里补上邮箱）。用户做选择时最怕选错了回不去，明说能补，选择成本就降到零。

**代价**：多维护一套认证代码，而它对本项目的实际价值有限。

### 9. 语言切换放在登录页，不只放在设置里

大多数产品把语言选项埋在设置页。但用户还没进产品就看不懂界面的话，他根本走不到设置页。所以登录注册页右上角常驻一个语言切换，移动端也不折叠。

语言切换不只是换界面文案。AI 消费总结和自然语言解析的输出语言跟着界面走，英文界面下模型返回英文；日期和货币用 `Intl` 按 locale 格式化，中文显示「2026年7月15日」，英文显示「Jul 15, 2026」。只翻译按钮而 AI 还在说中文，是半成品。

术语没有直译。「记一笔」是 Add expense 不是 Record one，「垫付」是 Paid 不是 Advance——直译出来会像财务软件，而这个产品的语气是朋友之间。

### 10. 每个群组一种货币，不做汇率换算

支持常见币种，但明确不做换算、不支持组内混币。

用户在旅行时想要的大部分只是"显示成日元"，而不是"按当天汇率折算成人民币"。后者要处理汇率时点、结算币种、历史汇率回溯，复杂度高出一个量级，而绝大多数场景用不到。

### 11. 只用一个色相

整个界面除了黑白灰只有珊瑚色。它的语义是"需要你处理的事"——主按钮是它（要你点），你欠别人的金额也是它（要你还）。别人欠你的钱不需要你做什么，用墨黑。

正数金额没有用绿色。红绿对立在财务界面里是惯例，但约 8% 的男性有红绿色觉障碍，而且引入第二个色相会破坏整体的克制感。

## 已知的局限

**认证是最薄的一层。** 只有邮箱加密码，没有邮箱验证、没有找回密码、没有第三方登录。另外这是本地演示项目，注册、登录、直接开始三条路径最终都接管同一份演示数据——真实产品里注册应该是一个全新的空账号。

**英文文案没有母语者校对过。** 术语表是自己定的，界面通读过一遍，但语气和习惯用法可能还有生硬的地方。

**Settlement 没有关联到具体的 Expense。** 一笔结算只记录转账双方和金额，无法回答"某笔账单结清了没有"。靠净额倒推目前够用，但按账单维度追踪结清状态做不了。关系画像里的"平均结清天数"因此用的是近似口径（匹配账单产生后双方之间的第一笔结算），界面上标注了样本量。

**收据识别和自然语言解析没有系统评估。** 只在少量真实输入上测过。已知的问题：相对日期（"昨天"）会被识别成当天；中文姓名有时匹配不上群组成员。这两个都不阻断使用——解析结果进的是可编辑表单，用户改一下就行，这正是那个设计要覆盖的场景。日期识别没有专门去修，因为改一下日历的成本是两秒钟，而让模型算准相对日期需要额外的规则层，性价比不高。

**没有并发处理。** 两个人同时记账可能丢数据。因为不上线，没有做乐观锁或事务隔离。

**没有真实的多人协作。** 数据在本地数据库里，无法分享给群组成员。替代方案是导出一张摘要图片发到群里——这其实更贴近现实中大多数人的做法。

**旅行时间轴没做。** 但数据模型里预留了 `tripId`、`location`、`photoUrls` 三个字段，后续加进来不需要迁移历史数据。

## 技术栈

Next.js（App Router）+ TypeScript + Prisma + SQLite + Tailwind CSS，测试用 Vitest。

选型的唯一标准是踩坑的人多、前后端一个仓库、本地一条命令跑起来。这个项目的目标是验证产品想法，不是技术选型练习。

国际化没有用 next-intl 或 i18next，而是一个 Context 加两个 JSON 文件。前者要改路由结构，对这个规模是过度设计。

## 本地运行

```bash
npm install
npx prisma migrate dev
npx prisma db seed
npm run dev
```

打开 http://localhost:3000

首屏可以注册、登录，或者直接开始，右上角可以切换中英文。三条路都会进入同一份演示数据：5 个成员、2 个群组、一年 100 多笔账单。其中「合租」群组的净额是刻意构造的，直接结算需要 4 笔转账，简化后只需要 3 笔。

想试真实的模型解析，在 `.env.local` 里设置：

```
OPENAI_API_KEY=你的 key
MOCK_AI=false
```

改完需要重启 dev server。不设置的话默认走 mock 模式，所有功能照常可用。

## 项目结构

```
src/lib/            纯业务逻辑，不依赖数据库，可直接单元测试
  settlement.ts     净额计算与最优结算
  split.ts          三种分摊方式
  direct-debts.ts   不做简化的逐对欠款
  group-stats.ts    群组维度聚合统计
  relationship.ts   两人之间的关系统计
  insights.ts       把统计结果翻译成自然语言
  parse-expense.ts  收据识别与自然语言解析（含 mock）
  format.ts         金额与日期格式化
  limits.ts         各项上限常量
src/i18n/           语言文件与切换逻辑
src/server/         数据库读写与认证
src/app/            页面
docs/PRD.md         完整需求文档
```

金额相关的计算全部在 `src/lib/` 里，页面和 API 层不出现任何金额加减逻辑，保证只有一个计算来源。
